# 买入卖出决策台 · 数据契约

> 本文冻结 YMOS V4 通用版买入卖出决策台的数据边界。前端、Console API、交易计划台和 Agent 适配都以此为准。

## 1. 产品边界

- 买卖决策台只提供**通用策略骨架**，不内置仓库中可选的作者扩展或任何参数默认值。
- 买卖决策台承载策略内核的动作审计与操盘留痕；交易计划台承载日频操盘计划。数据只允许从决策台单向流向计划台，计划台不能反向决定一笔投资是否成立。
- 本地正式版坚持 Markdown-first。浏览器缓存只用于草稿和体验，不是真相源。

## 2. 目录与文件生命周期

默认目录由 `Console/config.json` 的 `trade_dir` 决定：

```text
Brain/买入卖出决策/
├── 买卖决策_状态机.md
├── 标的_YYYY-MM-DD.md
├── 已平仓/
│   └── YYYY/
│       └── 标的_YYYY-MM-DD.md
└── 已作废/
    └── YYYY/
        └── 标的_YYYY-MM-DD.md
```

- `买卖决策_状态机.md`：账户资金基数、币种、可用期限、单笔上限和资金变动流水；同时保存最近一次成功行情刷新时的 `portfolioSnapshot`。快照只用于恢复上次显示、Agent 日常体检与复盘，单笔交易文件仍是持仓事实源。
- 开源包直接包含 `Brain/买入卖出决策/`、空状态机模板与 `已平仓/`。本地服务启动时会在仓库自身或外接 vault 中生成正式状态机并补齐相同目录；`file://` 页面预览数据不属于本契约的真相源。

`portfolioSnapshot` 的稳定分层：

- `accounts`：分币种的资金基数、净值、成本、市值、盈亏、待建计划与剩余可开。
- `positions`：当前股数、成本 / 现价、敞口、止损距离、论点、失效信号、退出动作与单笔告警。
- `health`：`normal / attention / critical` 总体状态、数据覆盖、告警列表与建议 P 系列路由。
- `agentRouting`：Agent 的读取顺序、事实源声明与去重后的 `suggestedRuns`。
- 根目录单笔文件：状态为 `计划中` 或 `持仓中`，数量有限、需要经常读取，因此不按月分层。
- 平仓后：追加平仓事件并移动到 `已平仓/YYYY/`；当单年文件很多时，服务端可以把新归档降到 `已平仓/YYYY/YYYY-MM/`。读取端必须兼容两种布局。
- 文件名由服务端根据标的、Ticker 和创建日期生成；前端不得提交任意写入路径。
- 建档时，服务端必须核对请求中的标的、Ticker、日期与 front matter、`ymos-trade-open` 完全一致；不一致时拒绝写入。

## 3. 单笔文件结构

文件由三部分组成：

1. YAML front matter：只保存当前状态事实，可被服务端更新。
2. `ymos-trade-open` JSON：创建时的买入逻辑档案，只写一次。
3. 一个或多个 `ymos-trade-event` JSON：后续事件只追加，不覆盖历史。

示例：

````markdown
---
ymos_trade: v1
标的: 示例公司
Ticker: DEMO
状态: 持仓中
策略: 通用策略
创建日期: 2026-08-01
持仓股数: 10
成本价: 100
实际投入: 1000
---

<!-- ymos-trade-open -->
```json
{
  "schemaVersion": 1,
  "kind": "open",
  "strategy": "general",
  "symbol": "示例公司",
  "ticker": "DEMO",
  "date": "2026-08-01",
  "thesis": {},
  "checks": {},
  "texts": {}
}
```

<!-- ymos-trade-event -->
```json
{
  "schemaVersion": 1,
  "kind": "prepare",
  "ts": "2026-08-01 20:30",
  "metrics": {},
  "checks": {},
  "texts": {}
}
```
````

## 4. 状态机

```text
买入逻辑建档
  → 计划中
  → 建仓准备 prepare/revise
  → 确认成交 fill（可重复：分批建仓）
  → 建仓中 ⇄ 持仓中
       建仓中：已有真实成交，但这份建仓计划还没建满
       持仓中：fill 事件带 complete: true 收口之后的终态
  → add / trim（变更建仓计划总额，状态回到 建仓中）/ tp / sl / adjust（可重复追加）
  → close
  → 已平仓并归档

计划中（零成交）
  → void（作废，必须写原因）
  → 已作废并归档到 已作废/YYYY/
```

状态取值：`计划中` / `建仓中` / `持仓中` / `已平仓` / `已作废`。

**为什么要有「建仓中」**：一份 100% 的建仓计划，现实里往往分成 30% + 30% + 40% 三笔买。
只有两态时，第一笔成交就会被记成「建仓完成」，剩下没执行的计划从系统里消失了 ——
真正需要被追踪的恰恰是「我的计划还有多少没执行」。所以状态由**人显式收口**，不由第一笔成交自动推进。

合法事件类型：

| kind | 含义 | 是否改变当前事实 |
|---|---|---|
| `open` | 买入逻辑建档 | 创建 `计划中` 文件 |
| `prepare` | 首次建仓准备 | 否 |
| `revise` | 成交前修订准备 | 否 |
| `fill` | 本次这一笔的实际成交（可多次） | **累加**股数与实际投入、按加权平均重算成本价；`complete: true` 时状态转 `持仓中`，否则停在 `建仓中` |
| `add` | 调大建仓计划（加仓） | 只改**建仓计划总额**，**不改股数与成本**；状态回到 `建仓中`，实际成交仍走 `fill` |
| `trim` | 缩减建仓计划 | 同上，方向相反；缩到等于已建仓金额时自动收口为 `持仓中` |
| `tp` | 止盈或减仓 | 部分卖出时更新剩余股数和剩余成本 |
| `sl` | 止损 | 部分卖出同上；全部退出进入 `close` |
| `adjust` | 调整价格止损或逻辑退出 | 追加旧规则 → 新规则 |
| `close` | 全部平仓与结果验证 | 状态改为 `已平仓` 并归档；已实现盈亏结转进账户资金基数 |
| `void` | 作废零成交的建仓计划 | 状态改为 `已作废` 并移入 `已作废/YYYY/`；不产生盈亏，不动资金基数 |

`add` / `trim` 事件的 `plan` 字段：

| 字段 | 含义 |
|---|---|
| `previousTotal` / `newTotal` / `delta` | 调整前后的建仓计划总额与增量（`delta` 有符号） |
| `direction` | `increase` / `decrease` |
| `filledAmount` / `filledShares` | 调整时已经建进去的金额与股数 |
| `settlesBuild` | 新计划是否已等于已建仓金额（true 时服务端顺手收口成 `持仓中`） |
| `reason` | 调整理由；`trim` 必填，`add` 选填 |

`void` 事件的 `void` 字段：`reason`（必填）/ `voidDate` / `plannedAmount` / `account` / `filledAmount`（恒为 0）。

`fill` 事件的 `fill` 字段：

| 字段 | 含义 |
|---|---|
| `shares` / `price` / `actualAmount` | **本次这一笔**的增量，不是累计值 |
| `batchIndex` | 这是第几笔成交 |
| `complete` | 是否就此收口（`true` → `持仓中`，`false` → `建仓中`） |
| `finalizeOnly` | 只收口、不追加成交（`shares` 为 0，必须同时 `complete: true`） |
| `plannedAmount` | 当前生效的建仓计划总额，写入 front matter 的 `建仓计划` |
| `filledBefore` / `filledAfter` / `progressPct` / `remaining` | 界面算出的进度快照，仅供阅读；账本以服务端累加为准 |

服务端强制执行上述迁移，而不是只依赖前端按钮锁：

- `prepare` 只能是计划中的首次准备；`revise` 只能发生在已有准备、尚未成交时。
- `fill` 只能作用于 `计划中` 或 `建仓中`，且必须已有 `prepare / revise`；本次金额由服务端按价格 × 股数重算，
  **累计股数、累计投入与加权成本价一律以 front matter 中的既有事实为基准推进** —— 界面算错了也污染不了账本。
- `fill` 事件里的 `complete` / `finalizeOnly` 必须与请求体一致，否则拒绝写入：文件和状态不允许讲两套故事。
- `finalizeOnly` 只在 `建仓中` 且已有真实仓位时合法。
- `add / adjust / tp / sl / close` 允许作用于 `建仓中` 或 `持仓中` 且已有成交事件的文件 ——
  **没建满不是继续扛着的理由**，止损与平仓不该等到建仓完成才解锁。
- `add` / `trim` 必须带 `planOnly: true` 与 `changesPositionFacts: false`；服务端只更新 `建仓计划` 与状态。
  `trim` 还必须带非空的 `plan.reason`，并且只允许作用于 `建仓中`（`持仓中` 没有未执行的计划可缩）。
- **建仓计划不得低于累计已建仓金额**（服务端按事件流累加校验，越界返回 400 `plan below filled amount`）。
  想降到已建仓以下，要表达的其实是「这笔到此为止」，对应动作是建仓收口，不是改计划。
- 部分卖出由服务端依据当前股数和事件中的卖出股数重算剩余仓位；`close` 必须卖完全部剩余股数。
- 全部平仓的终态事件必须是 `kind: close`；止盈或止损原因放在 `exitKind: tp / sl`，归档时当前股数和实际投入归零。
- `void` **只允许作用于 `状态 = 计划中` 且不存在任何 `fill` 事件的文件**，且必须带非空 `void.reason`。
  有过真实成交的一律走平仓归档 —— 有仓位就必须有出场记录，这是账要对得上的底线。

### 4.1 改计划 vs 作废

两者回答的是不同问题，不能互相替代：

| | 改建仓计划（`add` / `trim`） | 作废（`void`） |
|---|---|---|
| 回答 | **我改主意了** | **这条记录本就不该存在** |
| 典型场景 | 论点变弱想少买 / 赔率变好想多买 | 标的填错、重复建档、想法当天就被否 |
| 前提 | 已有成交（`建仓中` / `持仓中`） | 零成交（`计划中`） |
| 结果 | 文件留在主流程，计划变化留痕 | 移出主流程，归档到 `已作废/` |

用作废去实现「改主意」会洗掉整条认知链：重建等于新的 `open` 事件、新的冷却期、新的建仓决策日，
原来的论点与「我为什么把计划改小」这个动作全部消失。事后你会分不清
**主动缩减** 和 **从没打算买那么多** —— 而这两件事对复盘的意义正好相反。

## 5. 不可变与可变字段

不可变、只能追加：

- 原始买入论点与可证伪证据
- 每一次建仓准备、加仓、卖出、调整和结果验证
- 每个事件发生时的参数快照与理由

允许更新的 front matter 当前事实：

| 字段 | 含义 |
|---|---|
| `状态` | `计划中` / `建仓中` / `持仓中` / `已平仓` / `已作废` |
| `持仓股数` | 累计买入 − 累计卖出，当前还剩多少 |
| `成本价` | 多笔建仓的**加权平均**成本 |
| `实际投入` | 当前剩余仓位的成本金额 |
| `建仓计划` | 当前生效的建仓计划总额（会被 `add` 改大） |
| `建仓更新日` | 最近一笔成交的日期（还没收口时写这个） |
| `建仓完成日` | 收口为 `持仓中` 的日期 |

建仓进度 = 事件流里所有 `fill` 的 `actualAmount` 累计 ÷ `建仓计划`。
注意它与 `实际投入` 不是一回事：后者会因为减仓而下降，前者不会回退 ——
「我一共建了多少」和「我现在还剩多少」是两个问题。

任何接口都不得接收「整份旧文件内容然后覆盖」来修改历史事件。

## 5.1 决策审计

- 门禁未通过而点击动作按钮时，写入一条 `passed: false` 的审计；不得把被拦截误记成交易事件。
- 交易动作只有在对应 Markdown 成功落盘后，才写入 `passed: true` 的审计。
- 审计记录至少包含 `mode / target / ticker / tradeFile / missing`，并带 `ymos-decision-audit` JSON 块，供平仓复盘稳定识别 `gateBypassed`。
- 审计写入失败必须向 Human 明示；不能把失败静默吞掉。

## 6. 账户状态

账户状态支持 CNY / HKD / USD。每个账户至少包含：

- `capital`：资金基数，**不随行情变化，但随每一笔平仓结转滚动**
- `horizonFund`：资金可用期限，选择颗粒度为月
- `changes`：增资、减资、直接校正、平仓结转的时间和原因
- `maxSingleRatio`：单一标的上限

账户级还包含一张结转台账：

- `settlements[]`：`{ ts, file, symbol, account, realizedPnl, closeDate, capitalBefore, capitalAfter }`

Dashboard 统一口径：

```text
账户净值   = 资金基数 + 未结转已实现盈亏 + 浮动盈亏
待建计划   = 计划中的全额 + 建仓中还没建满的那一截
剩余可开   = 账户净值 − 持仓市值 − 待建计划
持仓口径   = 建仓中 + 持仓中（只要有真实成交，敞口就已经在市场里）
```

### 6.1 平仓结转

一笔交易归档为 `已平仓` 时，客户端必须：

1. 先确认 Markdown 已成功落盘；
2. 把该笔的**累计已实现盈亏**（含此前所有减仓）并入所属账户的 `capital`；
3. 往 `changes` 写一条 `settle_profit` / `settle_loss`，往 `settlements` 写一条台账；
4. 保存账户状态机。

出现在 `settlements` 里的文件，其已实现盈亏**不再**计入「账户净值」的未结转部分 ——
它已经变成本金了，再加一遍就是重复计算。

**为什么资金基数必须滚动**：它是单笔上限、仓位占比、期限判断的分母。
如果它永远停在开户那天的数字，赚了三年系统仍以为你只有起始那点钱，亏了三年又会继续按虚高的分母放行仓位。
分母不动的风控，是在用一个已经过期的自己做约束。

因此平仓时**卖出成交价是必填项**：没有它就算不出已实现盈亏，账户净值和资金基数都会停在原地。

行情只影响市值、浮动盈亏和净值，不修改资金基数，也不写入单笔决策文件。浏览器可以缓存最后一次成功行情和更新时间。

## 7. 通用规则与用户规则

代码内固定的是结构性红线：

- 资金期限与论点周期匹配
- 单笔占账户比例
- 最大风险可计算
- 价格止损必须有幅度；逻辑退出必须有可执行规则
- 计划金额与实际成交需要对账

`rules.json` 可以配置的是用户自己的判断问题、说明文字和纪律清单。它不能关闭上述结构性红线。

## 8. 兼容约定

- 新正式页面：`买卖决策台.html`
- 新正式路由：`/decide`
- `/sop` 是 `/decide` 的兼容别名；不再提供个人策略页面别名
- 旧 `Brain/决策审计/` 不自动迁移；Reader 继续可以读取
- 所有 JSON 块携带 `schemaVersion`；读取端对缺失版本按 `1` 处理
