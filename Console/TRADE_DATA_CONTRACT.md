# 买入卖出决策台 · 数据契约

> 本文冻结 YMOS V4 通用版买入卖出决策台的数据边界。前端、Console API、交易计划台和 Agent 适配都以此为准。

## 1. 产品边界

- 买卖决策台只提供**通用策略骨架**，不内置仓库中可选的作者扩展或任何参数默认值。
- 买卖决策台承载策略内核的动作审计与操盘留痕；交易计划台承载日频操盘计划。数据只允许从决策台单向流向计划台，计划台不能反向决定一笔投资是否成立。
- 本地正式版坚持 Markdown-first。浏览器缓存只用于草稿和体验，不是真相源。

## 2. 目录与文件生命周期

默认目录由 `Console/config.json` 的 `trade_dir` 决定：

```text
Brain/买入卖出决策/
├── 买卖决策_状态机.md
├── 标的_YYYY-MM-DD.md
└── 已平仓/
    └── YYYY/
        └── 标的_YYYY-MM-DD.md
```

- `买卖决策_状态机.md`：账户资金基数、币种、可用期限、单笔上限和资金变动流水；同时保存最近一次成功行情刷新时的 `portfolioSnapshot`。快照只用于恢复上次显示、Agent 日常体检与复盘，单笔交易文件仍是持仓事实源。
- 开源包直接包含 `Brain/买入卖出决策/`、空状态机模板与 `已平仓/`。本地服务启动时会在仓库自身或外接 vault 中生成正式状态机并补齐相同目录；`file://` 页面预览数据不属于本契约的真相源。

`portfolioSnapshot` 的稳定分层：

- `accounts`：分币种的资金基数、净值、成本、市值、盈亏、待建计划与剩余可开。
- `positions`：当前股数、成本 / 现价、敞口、止损距离、论点、失效信号、退出动作与单笔告警。
- `health`：`normal / attention / critical` 总体状态、数据覆盖、告警列表与建议 P 系列路由。
- `agentRouting`：Agent 的读取顺序、事实源声明与去重后的 `suggestedRuns`。
- 根目录单笔文件：状态为 `计划中` 或 `持仓中`，数量有限、需要经常读取，因此不按月分层。
- 平仓后：追加平仓事件并移动到 `已平仓/YYYY/`；当单年文件很多时，服务端可以把新归档降到 `已平仓/YYYY/YYYY-MM/`。读取端必须兼容两种布局。
- 文件名由服务端根据标的、Ticker 和创建日期生成；前端不得提交任意写入路径。
- 建档时，服务端必须核对请求中的标的、Ticker、日期与 front matter、`ymos-trade-open` 完全一致；不一致时拒绝写入。

## 3. 单笔文件结构

文件由三部分组成：

1. YAML front matter：只保存当前状态事实，可被服务端更新。
2. `ymos-trade-open` JSON：创建时的买入逻辑档案，只写一次。
3. 一个或多个 `ymos-trade-event` JSON：后续事件只追加，不覆盖历史。

示例：

````markdown
---
ymos_trade: v1
标的: 示例公司
Ticker: DEMO
状态: 持仓中
策略: 通用策略
创建日期: 2026-08-01
持仓股数: 10
成本价: 100
实际投入: 1000
---

<!-- ymos-trade-open -->
```json
{
  "schemaVersion": 1,
  "kind": "open",
  "strategy": "general",
  "symbol": "示例公司",
  "ticker": "DEMO",
  "date": "2026-08-01",
  "thesis": {},
  "checks": {},
  "texts": {}
}
```

<!-- ymos-trade-event -->
```json
{
  "schemaVersion": 1,
  "kind": "prepare",
  "ts": "2026-08-01 20:30",
  "metrics": {},
  "checks": {},
  "texts": {}
}
```
````

## 4. 状态机

```text
买入逻辑建档
  → 计划中
  → 建仓准备 prepare/revise
  → 确认成交 fill
  → 持仓中
  → add（加仓计划）/ tp / sl / adjust（可重复追加）
  → close
  → 已平仓并归档
```

合法事件类型：

| kind | 含义 | 是否改变当前事实 |
|---|---|---|
| `open` | 买入逻辑建档 | 创建 `计划中` 文件 |
| `prepare` | 首次建仓准备 | 否 |
| `revise` | 成交前修订准备 | 否 |
| `fill` | 计划转为实际成交 | 写入股数、成本价、实际投入，状态改为 `持仓中` |
| `add` | 加仓计划 / 压力测试 | 只追加计划事件，**不代表成交、不更新股数与成本**；实际加仓成交留给后续版本 |
| `tp` | 止盈或减仓 | 部分卖出时更新剩余股数和剩余成本 |
| `sl` | 止损 | 部分卖出同上；全部退出进入 `close` |
| `adjust` | 调整价格止损或逻辑退出 | 追加旧规则 → 新规则 |
| `close` | 全部平仓与结果验证 | 状态改为 `已平仓` 并归档 |

服务端强制执行上述迁移，而不是只依赖前端按钮锁：

- `prepare` 只能是计划中的首次准备；`revise` 只能发生在已有准备、尚未成交时。
- `fill` 只能发生一次，且必须已有 `prepare / revise`；成交金额由服务端按价格 × 股数重算。
- `add / adjust / tp / sl / close` 只允许作用于持仓中且已有成交事件的文件。
- 部分卖出由服务端依据当前股数和事件中的卖出股数重算剩余仓位；`close` 必须卖完全部剩余股数。
- 全部平仓的终态事件必须是 `kind: close`；止盈或止损原因放在 `exitKind: tp / sl`，归档时当前股数和实际投入归零。

## 5. 不可变与可变字段

不可变、只能追加：

- 原始买入论点与可证伪证据
- 每一次建仓准备、加仓、卖出、调整和结果验证
- 每个事件发生时的参数快照与理由

允许更新的 front matter 当前事实：

- `状态`
- `持仓股数`
- `成本价`
- `实际投入`

任何接口都不得接收「整份旧文件内容然后覆盖」来修改历史事件。

## 5.1 决策审计

- 门禁未通过而点击动作按钮时，写入一条 `passed: false` 的审计；不得把被拦截误记成交易事件。
- 交易动作只有在对应 Markdown 成功落盘后，才写入 `passed: true` 的审计。
- 审计记录至少包含 `mode / target / ticker / tradeFile / missing`，并带 `ymos-decision-audit` JSON 块，供平仓复盘稳定识别 `gateBypassed`。
- 审计写入失败必须向 Human 明示；不能把失败静默吞掉。

## 6. 账户状态

账户状态支持 CNY / HKD / USD。每个账户至少包含：

- `capital`：资金基数，不随行情变化
- `horizonFund`：资金可用期限，选择颗粒度为月
- `changes`：增资、减资、直接校正的时间和原因
- `maxSingleRatio`：单一标的上限

Dashboard 统一口径：

```text
账户净值 = 资金基数 + 已实现盈亏 + 浮动盈亏
剩余可开 = 账户净值 - 持仓市值 - 待建计划
```

行情只影响市值、浮动盈亏和净值，不修改资金基数，也不写入单笔决策文件。浏览器可以缓存最后一次成功行情和更新时间。

## 7. 通用规则与用户规则

代码内固定的是结构性红线：

- 资金期限与论点周期匹配
- 单笔占账户比例
- 最大风险可计算
- 价格止损必须有幅度；逻辑退出必须有可执行规则
- 计划金额与实际成交需要对账

`rules.json` 可以配置的是用户自己的判断问题、说明文字和纪律清单。它不能关闭上述结构性红线。

## 8. 兼容约定

- 新正式页面：`买卖决策台.html`
- 新正式路由：`/decide`
- `/sop` 是 `/decide` 的兼容别名；不再提供个人策略页面别名
- 旧 `Brain/决策审计/` 不自动迁移；Reader 继续可以读取
- 所有 JSON 块携带 `schemaVersion`；读取端对缺失版本按 `1` 处理
