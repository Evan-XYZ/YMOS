# 投资雷达 SOP（公开版）

> 暗号：`跑一下投资雷达` / `跑价格优先雷达` / `跑事件优先雷达` / `查一下价格`
> 输出：`Eyes/投资雷达/YYYY-MM/投资雷达_YYYY-MM-DD.md`

## 1. 定位

投资雷达把**市场变化、热门方向、持仓与 Watchlist**压缩成一份日常要看的报告，回答：

1. 最近市场在交易什么，风格发生了什么变化？
2. 哪些变化与我的持仓、Watchlist 或关注方向直接相关？
3. 下一步需要补价格、补事件、做研究，还是暂时无变化？

它不要求用户先完成 Strategy Profile，也不把 Profile 当作投研配置。当前方向和阅读重点来自 `持仓与关注/当前关注方向与投资偏好.md`；雷达的事实、价格和事件流程在该文件缺失时也必须照常运行。

## 2. 三种运行模式

| 模式 | 适合谁 | 必做 | 可跳过 |
|:---|:---|:---|:---|
| `balanced`（默认） | 想每天看一份综合报告 | 市场洞察 + 热门观察 + 状态机价格 + 事件映射 | 缺失的可选上游 |
| `price` | 主要盯持仓/Watchlist 价格 | 状态机 ticker + 价格路由 + 关键市场背景 | 全市场热门发现 |
| `event` | 主要盯宏观、财报、政策与板块事件 | 市场洞察 + 热门观察/追踪 + 对象事件 | 日常全量价格扫描 |

用户在暗号中指定模式时以用户为准；未指定则读可选的 `Eyes/投资雷达配置.md`；仍无配置使用 `balanced`。模式只决定投入精力，不改变数据真实性要求。

## 3. 输入：有就读，缺就降级

### 基础输入

- 最近 1-3 份 `Eyes/市场洞察/YYYY-MM/`；当日没有时可使用最近有效报告，但必须标记日期与 stale。
- 最近一份 `Eyes/投资雷达/YYYY-MM/`，用于连续性。
- `持仓与关注/持仓_状态机.md`、`持仓与关注/Watchlist_状态机.md`；空表是合法状态。

### 热门与跨市场输入

- 最近 1-3 份 `Eyes/A股热门观察/YYYY-MM/`；
- 最近 1-3 份 `Eyes/美股热门观察/YYYY-MM/`；
- 若阅读报告缺失，可回退到 `Eyes/Whats_Hot/YYYY-MM/` 与 `Eyes/美股热门追踪/YYYY-MM/`。

这些输入用于发现市场主线和跨市场映射。缺失不阻塞价格模式；在均衡/事件模式中必须降低相关结论置信度。

### 可选增强

- `持仓与关注/当前关注方向与投资偏好.md`：用于当前方向、跨市场映射、事件窗口和阅读优先级；
- 公司公告、财报、IR、监管文件与按需新闻源；
- `Eyes/投资雷达配置.md`。

Strategy Profile 属于下一层的判断接口，不是雷达输入；本 SOP 不读取 Strategy Profile。雷达可以把对象送入“待策略审阅”队列，但不得为了排序读取 Profile、把关注文件当成 Profile，或在 Profile 缺失时降级。

## 4. 日期与新鲜度

1. 窗口起点取上一份投资雷达日期；首次运行取最近有效市场洞察日期，最多回看 7 个自然日。
2. A 股、美股分别按各自交易日语义判断“最新”，不要用北京时间文件生成日替代美股交易日。
3. 窗口外文件只作背景，不增加信号权重；不能用旧文件假装当日上游。
4. 关键输入缺失或 stale 时，在报告头部说明影响范围；局部缺失不等于整份 `blocked_by_dependency`。

只有连最小模式所需输入都不存在时才阻塞：

- `price`：没有任何有效 ticker 且用户没有点名对象；
- `event`：没有市场洞察、热门报告或可用事件源；
- `balanced`：上述两条都不满足。

## 5. 执行流程

### Step 1：确定模式与扫描范围

读取用户暗号、可选配置和现有输入，记录：`mode`、市场日期、窗口、有效/缺失输入。忽略状态机中带 `（示例）` 或 `demo_only` 的行。

### Step 2：读取市场与热门报告

从最近报告中提取：

- 市场体温与进攻/防守风格；
- 过去几日持续强化、新出现、分化和退潮的方向；
- A 股与美股相互映射的已兑现、待兑现和证伪线索；
- 今天最值得 Human 阅读的上游报告及理由。

热门观察已经做过的板块归因与连续剧判断优先复用；雷达负责跨报告收敛，不重新编一套全市场选股。

### Step 3：价格扫描（`balanced` / `price`）

只扫描真实持仓 + Watchlist，或用户本次明确点名的 ticker：

```bash
python3 Eyes/scripts/price_scan_from_state.py \
  --date-tag "$(date +%Y%m%d)"
```

用户本次点名、但尚未写入状态机的 ticker，直接调用路由器，不先修改状态机：

```bash
python3 Eyes/scripts/fetch_price_router.py \
  --symbols "TICKER" \
  --output-dir "Eyes/投资雷达/Raw_Data/$(date +%Y-%m)" \
  --date-tag "$(date +%Y%m%d)"
```
路由：美股/Crypto 有 Finnhub Key 时走 Finnhub；A 股有 Tushare Token 时走 Tushare；港股与无 Key 场景回退 Yahoo Finance。输出位于 `Eyes/投资雷达/Raw_Data/YYYY-MM/`。

成功判定：至少一个路由输出可解析，ticker 与状态机映射一致，报价时间可见。某一数据源失败只影响对应 ticker；不得把旧价描述成实时价。

`查一下价格 TICKER` 只执行本步并汇报数据源/时间，不生成完整雷达。

### Step 4：事件映射（`balanced` / `event`）

把市场洞察、热门观察和已核验公司事件映射到持仓/Watchlist：

- 事实发生了什么；
- 对原有研究论点或失效信号有什么影响；
- 是需要补数、进入研究、进入策略审阅，还是无变化；
- 尚缺什么证据。

事件来源优先级：公司 IR/财报/交易所/监管原文 → 本地市场洞察 → 可信新闻源。只有价格事实而无可靠归因时写“归因待确认”。

### Step 5：轻量关注映射（可选）

- 没有关注文件：按市场重要性、持仓/Watchlist 直接相关性和证据强度排序。
- 有关注文件：增加当前方向、事件窗口、跨市场/产业链映射和阅读偏好，但不删除范围外重要事实。
- 雷达只写“当前研究关注”，不判断它是否已进入用户的策略能力圈；只有后续策略/动作任务才读取 Profile 并作出该判断。

雷达不输出最终买卖、持有、加仓、退出或再平衡结论。用户另行提出动作级请求时，才进入策略内核并检查 Profile；该检查不属于本 SOP。

### Step 6：去重并生成报告

同一对象同时出现价格、事件和跨市场信号时合并为一行，保留最高数据风险与研究优先级。雷达写报告，不迁移持仓/Watchlist 身份，不伪造已执行动作。

## 6. 报告契约

```markdown
# 投资雷达 - YYYY-MM-DD

> 模式：balanced / price / event
> 数据窗口与截至时间：
> 有效上游 / stale / 缺失：
> 关注增强：未配置 / 已读取（仅排序与关联）

## 今日定调
- 市场风格 + 相比上期变化 + 最重要的一件事

## 今天最值得看的报告与方向
| 来源报告 | 市场日期 | 核心增量 | 为什么重要 | 下一验证 |

## 持仓监控
| 对象 | 价格与时间 | 新增事件 | 对论点/失效信号影响 | 数据质量 | 下一步 |

## Watchlist 动态
| 对象 | 价格与时间 | 新增事件 | 研究缺口 | 数据质量 | 下一步 |

## 跨市场与板块信号
| 方向 | A股状态 | 美股状态 | 传导链 | 当前判断 | 下一验证 |

## 去重后的分析队列
| 优先级 | 对象/方向 | 触发 | 建议模块 | 所需资料 |

## 无变化、数据缺口与降级
-
```

空持仓或空 Watchlist 时，相关章节写“当前无真实对象”，其余市场与热门报告部分继续输出。

## 7. 成功判定

- 报告明确写出模式、日期窗口、数据截至与缺失输入。
- `balanced` 模式同时利用了可用的市场洞察、热门观察和状态机，而不是只复述一份上游。
- `price` 模式的价格能追溯到路由文件和报价时间；旧价明确 stale。
- `event` 模式的强归因能回到一手或可核验来源。
- A/美股热门观察缺失会降级，但不会让价格监控停摆。
- 关注文件缺失不会阻塞事实报告；Profile 缺失不是本任务的降级项，系统也不会悄悄替换成作者偏好。
- 报告只给研究队列和建议模块，不给最终交易动作。
